# Structs + multi-threaded runtime — research & roadmap

_Generated by the structs-runtime-research workflow. Reference for the implementation._

## Research 1

## What the proposal is

TC39 "JavaScript Structs: Fixed Layout Objects" (https://github.com/tc39/proposal-structs, spec https://tc39.es/proposal-structs/). Champions: Shu-yu Guo (@syg) and Ron Buckton (@rbuckton). **Stage 2** (advanced at TC39's 104th meeting). It is actually an umbrella of four shared-memory features: (1) unshared `struct`, (2) `shared struct`, (3) `SharedArray`, (4) high-level sync primitives `Atomics.Mutex` / `Atomics.Condition`. Goal: give JS a higher-performance, statically-analyzable alternative to `class` (fixed layout) plus a path to true multithreaded shared-memory objects (today only `SharedArrayBuffer` of bytes exists).

## Syntax

Two forms, both grammatically a class variant:
- `struct Box { constructor(x){ this.x = x; } x; }`  (unshared)
- `shared struct SharedBox { x; }`  (shared)
- `struct Point extends Box { constructor(x,y){ this.y=y; super(x); } distance(o){...} y; }` (structs may extend only other structs; shared structs only other shared structs)
- `new SharedArray(100)` — fixed-length shared array, read-only `length`.

## Semantics (unshared struct)
- Created at integrity level **sealed** → **fixed layout**: cannot add/`delete` fields, cannot reassign the prototype. Only the declared fields exist.
- All declared fields (including superclass fields) are pre-initialized to `undefined` BEFORE any user code can observe the instance.
- Methods are **non-generic**: `this` must be an instance of the struct or a subclass.
- Constructor return value is discarded (no return-override).
- Structs can extend only other structs.

## Semantics (shared struct) — the hard part
- **`null` prototype** (mandatory).
- **No instance methods** (data only; methods would be unshared closures). Static methods/fields live on the unshared constructor.
- Fields may reference **only primitives or other shared structs/shared arrays** — never an unshared object. This is the load-bearing invariant: "There are no references from shared objects to non-shared objects" (one-way reference rule).
- Instances are communicated to other agents via `postMessage` **without copying** — the receiver gets a handle to the SAME shared object, not a structured clone.
- No computed/symbol field names settled (open), and field set is fixed at declaration.

## Shared-struct MEMORY MODEL
- Default field access is **unordered** (racy, like plain reads/writes) but **never tears**: a read of a shared-struct field always sees exactly one prior write, never a mix — guaranteed regardless of memory order. (This is stronger than SAB byte views.)
- **Sequentially-consistent** access uses Atomics overloads that take a struct + field name instead of a TypedArray + index: `Atomics.load(struct, "field")`, `Atomics.store(struct, "field", v)`, `Atomics.exchange(...)`, `Atomics.compareExchange(...)`.
- Design principle: "Syntax that looks atomic ought to be atomic."

## Companion sync proposals (in the same repo/spec)
- `new Atomics.Mutex` — non-recursive mutex. `Atomics.Mutex.lock(mutex[, unlockToken])` (blocks, returns/charges an UnlockToken), `Atomics.Mutex.lockIfAvailable(mutex, timeout[, unlockToken])` (null on timeout), `Atomics.Mutex.tryLock(...)` (in V8's impl). `UnlockToken` has `.locked` getter, `.unlock()`, and `[Symbol.dispose]()` so it works with `using lock = Atomics.Mutex.lock(m)`.
- `new Atomics.Condition` — `Atomics.Condition.wait(cv, unlockToken)`, `Atomics.Condition.waitFor(cv, unlockToken, timeout[, predicate])`, `Atomics.Condition.notify(cv[, count=Infinity])`.

## Engine / V8 status
- Behind a flag in Chrome: `--enable-features=JavaScriptExperimentalSharedMemory` (or `chrome://flags/#enable-javascript-experimental-shared-memory`), M108+. Node exposes the V8 side via `--harmony-struct`.
- **No syntax in V8 yet** — V8 ships the runtime via a programmatic API, NOT the `struct` keyword: `let T = new SharedStructType(["x"]); let b = new T();`. Brand checks `SharedStructType.isSharedStruct`, `SharedArray.isSharedArray`. A `SharedStructType` registry keyed by an optional second arg exists.
- Cross-thread sharing requires `self.crossOriginIsolated === true` (COOP+COEP headers), same constraint as SharedArrayBuffer.
- V8 shared heap (crbug v8:11708): a heap shared between isolates; `kSharedOld`/`kSharedMap` allocation types; client isolates attach to a shared isolate; a shared GC stops all client isolates at a safepoint and scans their roots; initially no young generation, RO-heap-dependent, incremental marking initially disabled. String sharing (shared string table) underpins shared field string values. The mid-2025 ship target noted by commentators is widely viewed as optimistic.

## Transpilation / polyfill feasibility
- **Unshared `struct`**: largely transpilable to a `class` + `Object.seal` (fixed layout, pre-init fields, sealed). Loses the engine fast-path (the whole point) and cannot perfectly enforce non-genericity, but is semantically close. No official Babel plugin exists (Stage 2, no entry in babel/proposals).
- **`shared struct` / `SharedArray` / `Atomics.Mutex|Condition`**: **NOT polyfillable** — they require a real shared heap, cross-agent non-copying postMessage, tear-free shared fields, and atomic field ops, none of which exist in userland JS. A transpiler can only lower the *syntax* to V8's `SharedStructType(...)` constructor API where the engine supports it; the runtime capability cannot be shimmed.

**Recommendation:** Do not attempt to support `struct`/`shared struct` as a Treaty authoring/compile feature yet. Rationale: (1) Stage 2 — grammar (notably computed/symbol field names, expression form, and the `shared` modifier surface) can still change materially; (2) no engine ships the SYNTAX (V8 only has the programmatic `SharedStructType` API behind `--harmony-struct` / JavaScriptExperimentalSharedMemory + crossOriginIsolated), so any emit target is V8-only and flag-gated; (3) the runtime half (shared heap, cross-isolate GC, futex mutex/condition) is pure engine work Treaty cannot provide and cannot polyfill.

If/when you do invest, scope it precisely:
- PARSE: extend BOTH backends (oxc has no struct node in 0.133 — would require an oxc upstream feature or a Treaty pre-pass/fork; swc likewise) and keep them byte-identical via tools/backend-parity. Add a StructDeclaration discriminator + `shared: bool` + field-layout list to the neutral IR in d:\dev\treaty\libs\treaty-ivy\facade\src\parse\mod.rs (extend ClassWithDecorators/MemberInfo or add a sibling StructMeta).
- LOWER: emit unshared `struct` → `class` + `Object.seal` for broad targets; emit `shared struct`/`SharedArray`/`Atomics.Mutex|Condition` ONLY to a V8 SharedStructType target, gated, never to a polyfill.
- Treat the unshared-struct lowering as a safe, near-term experiment (it is essentially a sealed class); treat shared structs as a "wait for Stage 3 + a non-V8 second implementation" item. The honest scope is large: the valuable part (shared memory) is fundamentally a runtime/engine capability, not a compiler one.

**Risks:** - Stage 2 instability: grammar and semantics WILL likely change (champions flagged computed/symbol field names, private elements "ideally", and the `shared`-as-modifier surface as unresolved). Any parser/AST built now risks rework. Do not hard-code shape assumptions.
- oxc dependency gap: oxc 0.133 has no JS struct AST node (verified in oxc_ast-0.133.0/src/ast/js.rs). Supporting structs blocks on either an oxc upstream feature or a Treaty-side fork/pre-pass — a real maintenance cost given the repo's "contained behind ParseBackend" rule.
- Non-polyfillable runtime: shared structs / SharedArray / Atomics.Mutex|Condition cannot be shimmed in JS. Anything Treaty emits for them only runs on a V8 with the flag enabled AND a crossOriginIsolated context. Emitting them into a normal bundle would produce code that throws at runtime everywhere else — a silent footgun.
- Security/correctness invariant: the one-way reference rule (no shared→unshared refs) and tear-free-but-racy default fields are easy to get subtly wrong; a compiler that lowers naively could let an unshared object reach a shared field and crash the engine or violate the model.
- Single-engine reality: as of mid-2026 only V8 implements it (behind flags); SpiderMonkey/JSC have not shipped equivalents, so a "JS structs" feature is effectively Chrome/Node-only today. Stage 3 typically wants a second implementation — timeline is uncertain and the mid-2025 ship target was already optimistic.
- ASI hazard: the `[no LineTerminator here]` constraints after `shared` and `struct` are mandatory; a hand-rolled tokenizer that treats `struct`/`shared` as contextual identifiers can mis-parse real code (e.g. `let struct = 1`) if not careful.

## Research 2

## What TC39 structs syntax is (the surface to support)

Source: https://github.com/tc39/proposal-structs + /blob/main/SYNTAX.md.
- **Stage 2** proposal (champions Shu-yu Guo @syg, Ron Buckton @rbuckton). Syntax NOT frozen — "open questions" still include attaching methods to shared structs. Implementing now means tracking a moving target.
- Two new declaration forms, both class-shaped: `struct S { foo; constructor(){} bar(){} get baz(){} set baz(v){} }` and the shared variant `shared struct S { ... }` (a leading `shared` modifier; shared structs cannot have methods/private fields, fields hold only primitives/shared values, can only `extends` another shared struct or `null`).
- `struct` is in declaration position only (acts reserved-ish in that position); `shared` is a contextual prefix modifier. SYNTAX.md gives NO formal BNF — that ambiguity is itself a scope risk. The proposal text describes declarations only; struct *expressions* (`const X = struct {}` analog) are not specified, so a faithful node only needs the declaration form today.

## How oxc adds syntax (the three layers, and why a node is NOT a one-file change)

OXC's AST is **codegen-driven by an offline tool that does NOT ship in the published crates**. This is the single most important architectural fact for scoping.

1. **AST node (oxc_ast).** Nodes are plain structs/enums in `crates/oxc_ast/src/ast/{js,ts,literal,jsx}.rs` annotated with MARKER attributes: `#[ast(visit)]`, `#[scope(...)]`, `#[generate_derive(CloneIn, Dummy, TakeIn, GetSpan, GetSpanMut, ContentEq, ESTree, UnstableAddress)]`, `#[visit(...)]`. In the installed crate, `Class<'a>` is at `oxc_ast-0.133.0/src/ast/js.rs:2064`; `ClassType` enum (`ClassDeclaration`/`ClassExpression`) at :2138; the `Declaration` enum (where `ClassDeclaration = 34` lives) at :1199; `Statement` dispatches to these. A struct node would either (a) reuse `Class` with an added `r#type: ClassType::StructDeclaration` + an `is_shared` bool field, or (b) be a new `Struct`/`StructBody` pair. Option (a) is far cheaper downstream (every consumer that matches `Class` keeps working) and is the recommended shape.
2. **The marker attributes do nothing by themselves.** Confirmed via oxc.rs/docs/learn/architecture/ast-tools: `#[ast]`/`#[generate_derive]`/`#[visit]`/`#[scope]` are pure markers consumed by `tasks/ast_tools` (a binary crate in the oxc MONOREPO, not on crates.io). Running it regenerates, into `crates/oxc_ast/src/generated/`, a large set of files — all present and stamped "Auto-generated code, DO NOT EDIT DIRECTLY!" in the installed crate: `ast_builder.rs`, `ast_kind.rs` (the `AstKind`/`AstType` discriminants — `Class = 75` etc.), `derive_clone_in.rs`, `derive_content_eq.rs`, `derive_dummy.rs`, `derive_estree.rs` (the ESTree/JSON serialization), `derive_get_span{,_mut}.rs`, `derive_take_in.rs`, `derive_get_address.rs`, `derive_unstable_address.rs`, `get_id.rs`, and crucially **`assert_layouts.rs`** — compile-time `assert!(size_of::<Program>()==144)` / `offset_of!` checks for every node (the `oxc_ast_visit-0.133.0/src/generated/visit.rs` + `visit_mut.rs` are generated too; `visit_class` is at visit.rs:510, and `Declaration::ClassDeclaration => visitor.visit_class(it)` at :2066). A new AST node/field forces regeneration of ALL of these. You cannot hand-edit them sanely — the layout asserts alone make manual edits a trap.
3. **Parser (oxc_parser).** Hand-written recursive descent. Path for a struct: the keyword must be added to the **lexer keyword table** (`oxc_parser-0.133.0/src/lexer/kind.rs:488` `"class" => Class`, plus the perfect-hash byte handler at `byte_handlers.rs:519`), then statement dispatch (`js/statement.rs:134` `Kind::Class => self.parse_class_statement(...)`) gets a `Kind::Struct` arm, and `js/class.rs` (`parse_class`, :59) is generalized to carry the struct/shared flags. `shared` is contextual (legal as an identifier), so it needs lookahead — `shared struct` only when `struct` follows — mirroring how oxc disambiguates `accessor`/`using`. This is real, careful parser work, not mechanical.

Net: a single new syntactic form touches ~3 hand-edited files PLUS a forced regen of ~15 generated files via a tool that only exists in the monorepo. Optionally semantic (`oxc_semantic` scope/binding — Treaty does NOT use this on the Ivy path per SWC-BACKEND-PLAN §2/§3, so it can be skipped) and codegen (`oxc_codegen` printer — Treaty's emit does NOT round-trip structs; it emits Ivy, so also skippable for Treaty's use).

## The three options, judged against Treaty's reality

**A. Contribute upstream to oxc.** Correct long-term, but: proposal is Stage 2 with unfrozen syntax; oxc's policy (mirrors swc's — see github.com/swc-project/swc discussions) is to track spec'd/advanced behavior, and oxc has an open issue (#17285) explicitly about declining non-standard JS dialects. A Stage-2, syntax-unstable feature is unlikely to be accepted upstream now. Even if accepted, Treaty is PINNED at 0.133 and would wait for a release + bump.

**B. Fork oxc.** Technically the "complete" path, but the maintenance cost is severe and lands squarely on the part of the codebase Treaty deliberately engineered to keep oxc bumps MECHANICAL. A fork means: vendoring `tasks/ast_tools`, re-running codegen on every node change, and re-vendoring/re-generating on EVERY upstream 0.133→0.x bump (the OXC-MIGRATION-HARNESS.md promise that "future oxc bumps are mechanical" breaks — a fork makes them a 3-way merge of generated files + layout asserts). This is the opposite of `migration/OXC-MIGRATION-HARNESS.md`'s design intent.

**C. Pre-pass / desugar before oxc (RECOMMENDED).** Treaty already owns a pluggable authoring layer (`apps/rust/authoring`, the .treaty/JSX plugins) and a parse SEAM (`ParseBackend`). A pre-pass lexes just enough to find `struct`/`shared struct` declarations and rewrites them to a `class` + a marker the downstream walk understands, BEFORE oxc parses. Because the struct grammar is class-shaped, the rewrite is largely token-level (`struct`→`class`, strip/record `shared`), preserving byte spans for everything inside the body. This keeps oxc 0.133 UNFORKED, keeps bumps mechanical, and keeps swc parity (see below) trivially achievable because both backends parse the SAME desugared `class`. The cost is the pre-pass has to handle the lexical edge cases (ASI, `struct` as an identifier elsewhere, nested structs) honestly — but that is a contained, testable Rust module, not a fork.

## How struct/shared-struct nodes flow through Treaty's neutral IR

The neutral IR is built for classes and needs only additive flags — confirmed by reading `libs/treaty-ivy/core/src/neutral.rs` and `libs/treaty-ivy/facade/src/parse/mod.rs`:
- `ClassWithDecorators` (neutral.rs:539) — add `is_struct: bool` + `is_shared: bool`. `lower_class` in `parse/oxc.rs:304` (and its swc twin) fills them from `Class::r#type`/the new flag. Members already flow through `MemberInfo`/`MemberKind` (neutral.rs:431) unchanged — structs have the same field/method/getter/setter shapes.
- Spans are byte-absolute on both backends (oxc absolute; swc rebased −1, documented in `parse/swc.rs`), so `span_text`/decorator/object extraction need no change.
- `ParseOutput.top_level` (`NTopStmt`) and `NExpr` need no new variant for the declaration form. If struct *expressions* are ever specified, `NExpr` gets one additive variant.
- The parse-parity gate (`parse/mod.rs` `mod parse_parity`, the `SOURCE_CORPUS`/`assert_parity` harness) extends with struct fixtures; `ParseOutput` derives `PartialEq`, so one `assert_eq!` proves oxc≡swc byte-for-byte.

With approach C, even the AST-flag change is avoidable: the desugar emits `class`, and the "this was a struct" bit is recorded out-of-band (a side table keyed by name span) and merged into `ClassWithDecorators` during lowering — zero oxc-type changes, fully inside the facade.

## swc parity (the second backend)

`libs/treaty-ivy/facade/src/parse/swc.rs` is a full second backend gated 1:1 by `tools/backend-parity` + the in-crate `parse_parity` tests. swc's stated policy (swc-project discussions) is that core will never support non-standard/proposal syntax until it's spec'd — so `swc_ecma_parser` will NOT parse `struct`/`shared struct` either. That kills approach B's parity story (you'd have to fork swc TOO, or the swc backend can never compile struct sources). Approach C is the only one that keeps BOTH backends 1:1 for free: the pre-pass desugars to `class` once, and both engines parse identical input.

## Maintenance story (the harness)

`migration/OXC-MIGRATION-HARNESS.md` makes bumps mechanical PRECISELY because the only oxc-AST consumer is `parse/oxc.rs` and the only emit consumer is `emitter.rs`. A fork (B) directly defeats this: every bump becomes a regenerate-and-merge of `crates/oxc_ast/src/generated/*` + `assert_layouts.rs` against upstream. A pre-pass (C) preserves it — it adds ONE new Treaty-owned module (the desugarer) plus additive IR flags, both covered by the existing `api-breakage-scout`→`oxc-migrate`→`backend-parity`/`parse_parity`→matchGolden gate chain unchanged.

**Recommendation:** Do a Treaty-owned PRE-PASS (desugar `struct`/`shared struct` → `class` + side-table marker) in the authoring/parse seam, NOT a fork and NOT (yet) an upstream contribution. Concretely: (1) add a small `struct_desugar` module that tokenizes enough to locate `struct`/`shared struct` declarations and rewrites `struct`→`class` while recording (name-span → {is_struct, is_shared}) — span-preserving for the body so all downstream span recovery is unaffected; run it before `ParseBackend::parse_module`. (2) Merge the side-table bits into `ClassWithDecorators` (additive `is_struct`/`is_shared` flags) during `lower_class`, on BOTH oxc and swc backends, so the neutral `ParseOutput` is byte-identical. (3) Extend the existing `parse_parity` corpus + `tools/backend-parity` with struct fixtures (the `ParseOutput` PartialEq gate proves oxc≡swc). (4) Decide the SEMANTICS: structs are class-shaped but with fixed layout / restricted shared variant — define how Treaty compiles them (likely: treat a non-shared struct as a class for Ivy purposes; flag shared structs as currently unsupported-for-decoration with a clear diagnostic) before wiring emit. Defer any fork/upstream work until the proposal reaches Stage 3 and oxc ships native support, then drop the pre-pass and consume the native node behind the same seam.

**Risks:** - LEXICAL CORRECTNESS of the pre-pass is the real risk: `struct` is a valid identifier today and `shared` is contextual, so a naive text rewrite can corrupt code that uses those names (`let struct = 1`, `shared.foo`). The desugarer must be a proper mini-lexer respecting strings/comments/regex/template literals and only rewrite in declaration position — same class of hazard called out in memory `no-regex-verification` (NEVER regex-match code). Must be AST-or-token-accurate, with a fixture corpus.
- SYNTAX INSTABILITY: Stage 2, no BNF, open design questions (shared-struct methods). Anything built now may need revision; keep the surface minimal and flag-gated.
- SEMANTIC GAP: structs have fixed layout, no field add/delete, shared structs forbid methods/private fields and only hold primitives/shared values. If Treaty treats a struct as a plain class for Ivy, that is a lossy approximation — fine for parsing/authoring, wrong if Treaty ever needs struct semantics. Shared structs in particular should probably emit an explicit "unsupported as a decorated Angular type" diagnostic rather than silently compiling.
- FORK PATH (if chosen anyway) breaks the mechanical-bump invariant: `tasks/ast_tools` is monorepo-only, and `assert_layouts.rs` makes hand-editing generated files a compile-time trap; every oxc bump becomes a generated-file 3-way merge. This is the explicit anti-goal of migration/OXC-MIGRATION-HARNESS.md.
- UPSTREAM PATH is gated on oxc policy (issue #17285 — they decline non-standard dialects) and the pin at 0.133; not actionable until the proposal advances and oxc releases support.
- SWC parity: swc core will not add proposal syntax, so any approach that relies on oxc natively parsing structs (fork) leaves the swc backend unable to compile the same source — breaking the `tools/backend-parity` 1:1 contract. Only the pre-pass avoids this.

## Research 3

SCOPE: Research-only (no files edited). Question = can libs/runtime (Nova) support (a) fixed-layout structs and (b) SHARED structs across THREADS/workers. Short answer: real SharedArrayBuffer+Atomics shared MEMORY across worker isolates is achievable today (Nova already ships it; net.rs already proves the OS-thread worker pattern). Shared fixed-layout OBJECTS (TC39 shared structs / cross-thread object refs) are a very large, mostly-greenfield effort that Nova does NOT support and cannot cheaply be made to support given its moving/compacting per-agent heap.

== NOVA VALUE / HEAP / GC MODEL (the constraint that dominates everything) ==
Source: vendored Nova at C:\Users\Jordan\.cargo\git\checkouts\nova-f1c1e1d37112fce3\bece61a (rev bece61a, the rev pinned in libs/runtime/Cargo.toml).
- Data-oriented "Struct of Arrays" heap (heap/README.md, ARCHITECTURE.md): each object TYPE lives in its own Vec/SoAVec; a JS Value is a {u8 type tag, u32 index} handle — an INDEX into a per-Agent heap vector, NOT a pointer. There is no inline-property object; everything is referenced by index.
- GC is a MOVING, COMPACTING tracing mark-and-sweep (GARBAGE_COLLECTOR.md, heap/README.md "## Garbage collection"): live objects are shifted down within their vectors during GC, so "most Values that remain in the heap move during garbage collection" and every internal reference index is rewritten post-compaction. Handles are "unrooted" and invalidated by any GC; safety is enforced via the GcScope / NoGcScope / Scoped borrow-checker dance (bind/unbind/scope/reborrow). This moving design is the single biggest obstacle to cross-thread object refs: a raw cross-thread pointer to a heap object would dangle the instant the owning agent GCs.
- The Agent owns its Heap BY VALUE and holds RefCell<Vec<HeapRootData>>, Vec<NonNull<Vm>>, raw execution-context stack (agent.rs:866-916). It is inherently NOT Send/Sync — one Agent = one realm = one OS thread. host_hooks is &'static dyn HostHooks with NO Send/Sync bound (agent.rs:872), confirming single-thread intent. A code comment (agent.rs:876) notes heaps are currently per-agent ("With Realm-specific heaps we'll need a side-table") — there is NO shared heap and no agent-cluster concept in Nova.
- Public engine API (agent.rs:685-809): GcAgent::new(opts, &'static hooks) -> create_realm -> run_in_realm(closure(&mut Agent, GcScope)). Up to 256 realms per agent, but all on the one thread.

== HOW FIXED-LAYOUT (UNSHARED) STRUCTS WOULD BE ALLOCATED ==
Feasible but non-trivial; it is a new exotic object type in Nova's heap:
- Add a new SoA heap vector (e.g. structs: SoAVec<(ShapeIndex, FixedSlots)>) keyed by an immutable Shape/hidden-class. A struct handle is the usual {tag,u32}. Fields are a fixed inline slot array (Value handles), no dictionary, prototype fixed at declaration. This matches the SoA philosophy well (heap/README.md literally says "this is exactly what structs are in systems programming languages").
- Each slot still holds a Value HANDLE, so structs participate in mark/sweep + compaction like any heap object (implement HeapMarkAndSweep: mark_values traces each slot, sweep_values rewrites each slot's index). This is the established pattern seen in array_buffer/data.rs and shared_array_buffer/data.rs (the SharedArrayBufferRecord impls).
- This is pure single-thread work, no concurrency hazard, but it touches Nova internals (new heap vector, new Object variant, GC trace/sweep, constructor/property exotic methods, the bytecode interpreter's get/set fast paths). It is realistically an upstream Nova contribution, not something doable from inside libs/runtime (which only sees the public API). Treaty pins a Nova git rev, so this means carrying a fork/patch.

== THE HARD PART: SHARED STRUCTS ACROSS THREADS ==
Two genuinely different capabilities; the user is conflating them and they have wildly different cost:

(A) SHARED MEMORY (bytes) across worker isolates — ACHIEVABLE NOW, Nova already has the machinery:
- Nova ships SharedArrayBuffer + Atomics, and they are in nova_vm's DEFAULT feature set (nova_vm/Cargo.toml [features] default = [... "array-buffer","shared-array-buffer","atomics" ...]). libs/runtime depends on nova_vm with defaults intact (Cargo.toml only sets default-features=false on flate2 and rustls, NOT on nova_vm) — so SAB+Atomics are ALREADY COMPILED INTO the Treaty runtime today, just not surfaced to JS.
- The backing store is designed for cross-thread sharing: SharedDataBlock (ecmascript/types/spec/data_block.rs:609) is #[repr(C)] with an atomically reference-counted off-heap allocation (rc AtomicUsize before the bytes), is explicitly `unsafe impl Send`/`unsafe impl Sync` (data_block.rs:616-619), and uses a RacyPtr<u8> from the `ecmascript_atomics` crate (RacyStorage/RacyMemory) — the bytes are touched ONLY via racy-atomic ops, never as a Rust &[u8] (the module note: "it is not possible to access the backing bytes of a SharedDataBlock from Rust under any circumstances" because JS's memory model permits data races that are UB in Rust).
- Cross-agent Atomics.wait/notify is fully implemented and coordinated OFF the agent heap: the waiter list lives INSIDE the shared allocation (lazily CAS-initialized AtomicPtr<Mutex<WaiterLists>>), keyed by byte index (data_block.rs WaiterRecord/WaiterList/WaiterLists; atomics_object.rs notify body uses data_block.get_waiters() -> Mutex). So two INDEPENDENT agents on different OS threads holding clones of the same SharedDataBlock genuinely block/wake each other. atomics_object.rs imports std::thread::JoinHandle and implements wait/waitAsync/notify per spec.
- The exact integration seam exists as PUBLIC API: SharedArrayBuffer::get_data_block(&Agent) -> &SharedDataBlock (clone-able, Send) and SharedArrayBuffer::new_from_data_block(&mut Agent, SharedDataBlock, NoGcScope) (shared_array_buffer.rs:93 and :98-110). So the worker plumbing is: in agent A get the SharedDataBlock, .clone() it (bumps the atomic rc), move the clone across a thread/channel boundary to worker agent B, call new_from_data_block to mint a fresh SAB handle in B's heap pointing at the SAME bytes. The SAB OBJECT is per-agent; the BYTES are shared. This is exactly the Node/Bun worker_threads + SharedArrayBuffer model.
- Only the SAB handle and its per-agent backing_object are in each agent's moving heap; the shared bytes are off-heap and immovable, so compaction never invalidates them. This is why SAB works and arbitrary shared objects do not.

(B) SHARED OBJECTS / fixed-layout shared structs (cross-thread object references) — VERY LARGE, essentially greenfield, NOT supported:
- Per the TC39 structs/shared-structs proposal (Stage 2): shared structs are fixed-layout objects whose fields "can only reference primitives or other shared structs ... they cannot point to unshared values"; "the shared and non-shared heaps are conceptually separate, with direct references only going one way"; instance methods are forbidden (functions are deeply unshareable); they are "communicated to other agents without copying" (postMessage shares by reference); synchronization is Atomics.Mutex (returns a non-shared UnlockToken) + Atomics.Condition; field access is unordered unless via Atomics.load/store/exchange/compareExchange.
- To support this, Nova would need a SEPARATE SHARED HEAP that is (i) NOT owned by any single Agent, (ii) either non-moving or moved only under a stop-the-world barrier across ALL participating agents, (iii) its own concurrent/coordinated GC, and (iv) a one-way reference invariant enforced at write time (a shared struct field may never store an unshared handle). Nova has none of this: its heap is per-agent, moving, and traced by a single mutator thread (GARBAGE_COLLECTOR.md only speculates that "with careful work it should be possible to enable partially concurrent MARKING" — and even that is just marking, not a shared mutable heap with cross-thread mutators).
- V8 itself needed a dedicated shared heap + Isolate-Groups to do this (cross-isolate shared objects are impossible across an IsolateGroup boundary; a shared heap had to be built; a SharedStructType registry prototyped). That is the scale of work; it took Google years and is still not shipped to stable. Replicating it in Nova is a multi-quarter engine-rewrite, very likely requiring upstreaming, and is NOT a libs/runtime-level task.

== HOW worker_threads / Web Workers FIT (the realistic vehicle) ==
- The runtime architecture memory already commits to this exact model and to its limit: runtime-node-architecture.md says the multi-threaded flag "must mean a worker pool of INDEPENDENT Nova isolates, each on its own OS thread with its own single-threaded event loop, communicating via message-passing + structured-clone (the worker_threads / web Worker model)" and that "shared-memory single-realm threading is impossible by design." That is correct and matches Nova's design.
- The precedent already exists in-tree: libs/runtime/src/node/net.rs runs a process-wide Reactor (OnceLock<Mutex<Reactor>>) with background std::thread workers (JoinHandle, channels) for blocking socket I/O, polled non-blockingly by the single JS thread via the event loop. A Worker is the same shape: spawn an OS thread, build a fresh GcAgent::with_node_compat there, run its own event_loop.run_until_idle, and exchange messages over std::sync::mpsc channels. structured_clone.rs already implements the copy semantics for messages; it ALREADY special-cases SharedArrayBuffer to be "shared by reference, not copied" (structured_clone.rs:155-159) — so a postMessage that carries an SAB hands across the cloned SharedDataBlock rather than copying bytes. (Today there is NO worker_threads/Worker/MessagePort/postMessage module — confirmed by repo-wide grep: only comments mention them — so this whole module is to-be-built.)
- A node:worker_threads module would slot into the existing lazy builtin registry exactly like the other node/*.rs modules (mod.rs BUILTINS table + a worker_threads.rs leaf), using the established HostState/NodeCtx/event_loop wiring.

== CONCURRENCY + GC-SAFETY CHALLENGES (concrete) ==
1. Agent is !Send/!Sync: you cannot move a live Agent or any Value handle across threads. Each worker MUST construct its own GcAgent on its own thread. Only Send+Sync payloads (the SharedDataBlock, primitives, serialized/structured-cloned bytes) may cross.
2. Moving GC vs shared pointers: any cross-thread reference into a moving heap is a use-after-move waiting to happen. SAB sidesteps this by putting bytes OFF-heap behind a Send/Sync atomic-rc allocation; shared structs cannot, which is the whole reason they need a separate shared heap.
3. The shared bytes are deliberately un-dereferenceable from safe Rust (RacyMemory only) — so any "shared struct over SAB" userland shim must do typed atomic loads/stores, never hand out a Rust slice.
4. Atomics.wait blocks the OS thread — only legal on a worker whose agent CanBlock (AgentOptions.no_block=false; can_suspend()); never on the main/event-loop thread (matches the spec [[CanBlock]] rule). Today JsRuntime sets no_block:false (lib.rs:135), so this needs a per-worker policy.
5. One-way reference invariant (if real shared structs were ever attempted): every shared-struct field write must be guarded so an unshared handle can never be stored; violating it lets one agent's GC free memory another agent still reads.

== MEMORY/RUNTIME-SELECTION CAVEAT ==
Per runtime-selection-rule.md, Nova is ONLY for the pure-Rust/axum path; JS-runtime backends (Bun/Node/edge) use the system runtime directly. So this shared-struct work matters only for the self-contained Rust host. That bounds the payoff and is worth weighing before investing.

**Recommendation:** Ship in two clearly-separated phases and DO NOT promise true shared structs.

PHASE 1 (do this; weeks, not quarters) — surface what Nova already has:
1. Expose SharedArrayBuffer + Atomics to JS as globals (the engine support is already compiled in via nova_vm default features; today it's just not wired into the realm globals). Verify via a Node-conformance corpus test.
2. Build node:worker_threads (+ Worker, MessagePort, postMessage) as a new lazy builtin leaf, modeled on net.rs's OS-thread+channel pattern: each Worker = its own GcAgent::with_node_compat on a std::thread with its own event loop; messages travel as structured-clone bytes over mpsc.
3. Wire the SAB sharing path: postMessage of an SAB clones the SharedDataBlock (get_data_block().clone()) and re-materializes it in the target worker via new_from_data_block — bytes shared, no copy. structured_clone.rs already declares SAB share-by-reference, so honor that in the message marshaller.
This delivers genuine shared-memory multithreading (parallel workers + shared mutable bytes + Atomics/locks) — the 90% use case — with NO engine GC surgery.

PHASE 2 (optional, gate hard) — fixed-layout UNSHARED structs as a new Nova heap object type (a Nova upstream/fork task): a new SoA heap vector keyed by an immutable Shape, fields as inline Value slots, full HeapMarkAndSweep. Single-thread, safe, but touches Nova internals + the pinned git rev, so it means carrying a patch/fork and an upstream conversation. Justify only if there's a concrete perf win in the macro/SSR path.

DO NOT attempt true cross-thread SHARED structs (a separate shared GC heap) on Nova now — it is a V8-shared-heap-class rewrite, almost certainly upstream, multi-quarter, and high-risk. If userland needs "shared mutable fixed-layout objects" before TC39/engines ship it, provide a Tier-2-shim: a JS/Rust class laying typed fields over a SharedArrayBuffer with Atomics + a userland mutex (fields limited to scalars/offsets). Frame all of this against runtime-selection-rule.md: this only benefits the pure-Rust/axum host, so size the investment accordingly.

**Risks:** - Honesty/scope: "SHARED structs across threads" as the user phrased it (TC39 shared structs = cross-thread object references) is NOT realistically buildable on Nova in any near term — it needs a separate, non-moving, independently-GC'd shared heap (what V8 spent years building as the shared heap + IsolateGroups, still not stable). Phase-1 SAB+Atomics+worker_threads is real and shippable; equating the two would over-promise.
- Moving/compacting GC is the hard wall: any cross-thread reference into a per-agent heap dangles on the next GC. SAB only works because its bytes are off-heap behind an atomic-rc Send/Sync allocation. There is no cheap way around this for arbitrary objects.
- Engine fork risk: both real shared structs AND even unshared fixed-layout structs require editing nova_vm internals (heap vectors, GC trace/sweep, exotic object methods, interpreter fast paths). libs/runtime only sees Nova's public API, so this means forking/patching a pinned git rev (rev bece61a) and an upstream relationship — a maintenance burden the codebase has so far avoided.
- Nova maturity: Nova is pre-1.0 (the Cargo.toml comment notes 1.0.0 was broken both ways, hence tracking git main). SAB/Atomics are implemented and default-on but their cross-thread paths are not exercised by the Treaty test suite yet — Phase 1 must add conformance tests before claiming it works. The data_block.rs cross-thread code is heavy unsafe (RacyPtr, manual atomic rc, CAS'd waiter map) — trust-but-verify with stress tests (ABA on rc, waiter-map init race, Atomics.wait/notify under contention).
- Atomics.wait blocks the OS thread: must be forbidden on the main/event-loop agent (use waitAsync there); only CanBlock workers may block, or the runtime deadlocks/stalls the loop.
- Unhandled-rejection + error propagation across workers is currently a no-op (core.rs promise_rejection_tracker is a documented no-op); a worker that throws needs a defined propagation-to-parent story.
- Determinism/event-loop predictability: the runtime memory explicitly wants workers to "behave with an event loop so users know what to expect" — true parallelism + shared mutable memory reintroduces data races and non-determinism that the single-isolate model avoided; document the contract.
- Payoff is bounded by runtime-selection-rule.md: only the pure-Rust/axum host uses Nova at all; Bun/Node/edge targets use the system runtime. So the entire investment serves one backend — weigh before committing engine-level work.

## Research 4

## TL;DR

The repo already has BOTH halves of a Node-compat story: a substantial Nova-based runtime (`libs/runtime`, ~30.8k LOC, 28 `node:` builtin files, 483 unit tests) AND a working, no-AI conformance harness (`tools/node-conformance`). But the harness today runs a **69-file, hand-authored, curated corpus** (68 pass / 1 skip = "100% of 68 run"), NOT the real upstream Node.js test suite. The "100%" is honest about its denominator but the denominator is ~69 self-written cases, versus Node's `test/parallel` which has ~4,500+ files. The path to a *measurable, credible* Node-compat score is to vendor a config-driven subset of real upstream Node `test/parallel` files (the Deno model) and report executed-pass-rate per module. The single biggest architectural blocker is the runtime's eval wrapper.

## 1. The Node.js test suite structure (external, cited)

- **Layout**: Node's functional suite lives under `test/` with the high-value buckets being `test/parallel/` (tests safe to run concurrently — the bulk, files named `test-<module>-<topic>.js`, e.g. `test-buffer-alloc.js`, `test-fs-*.js`, `test-crypto-*.js`) and `test/sequential/` (order/shared-state-dependent, run serially). `test/parallel` alone is **thousands of files** (GitHub's listing shows 1,000 displayed + "3,556 entries omitted", so ~4,500+). Sources: [nodejs/node test/parallel], [issue #49487], [commit 25d4b5b].
- **Shared harness**: nearly every test does `require('../common')` (the `test/common/` module), which provides `mustCall`/`mustNotCall` (assert a callback fires exactly N times — its absence fails the test at process exit), `hasCrypto`/`hasIntl` capability gates, `skip()`, platform skips, and a `Flags:` comment convention (some tests must be re-spawned with flags like `--expose-internals`). A test that never loads `common` won't get re-spawned with needed flags. Tests use the built-in `assert` module and **throw on failure**; the *runner* (historically `python tools/test.py`, now also the green/red of `node --test`-style spawning) treats a non-zero exit / thrown error as fail. Sources: [test/common], [commit 1795202], [PR #17257].
- **The WPT subset**: `test/wpt/` is a runner (`WPTRunner` in `test/common/wpt`) that executes a *vendored subset* of upstream Web Platform Tests stored in `test/fixtures/wpt`. Each module has a **`status/<name>.json`** declaring expected failures / skips / build requirements. The subset Node ships covers the web-standard surfaces a runtime must also pass: **`url`** (URL/URLSearchParams), **`encoding`** (TextEncoder/TextDecoder), **`streams`** (WHATWG ReadableStream/WritableStream/TransformStream), **`console`**, plus webcrypto/structured-clone/etc. The runner summarizes pass/fail against the status file. Sources: [nodejs/node test/wpt], [test/wpt/README], [PR #33297], [commit b68734b].

## 2. What "Node-compatible, pass all test cases" realistically means

It is effectively unbounded and nobody claims it. "Pass all of `test/parallel`" implies implementing essentially the entire Node surface (incl. `worker_threads`+`MessagePort`, `vm` contexts, `cluster`, `dgram`/`dns`, `inspector`, `async_hooks`, `perf_hooks`, the full streams object model with backpressure/`highWaterMark`, complete `crypto` incl. asymmetric keys/X.509/WebCrypto, ICU-backed `Intl`, exact error `code`s and message text, ESM loader semantics, etc.) AND matching Node's *observable behavior to the byte* (error `.code`, `.message`, property enumeration order, deprecation warnings). Many upstream tests also poke V8/libuv internals (`--expose-internals`, `process.binding`, GC timing) that are not "Node API" at all and are not meaningfully portable to a different engine (Nova vs V8). So the realistic target is **"pass the behavioral subset of `test/parallel` for the modules we choose to support, minus internals/engine-specific cases, reported as executed-pass-rate per module"** — exactly what Bun and Deno do.

## 3. How Bun + Deno measure / report Node compat (the models to copy)

- **Bun**: runs "thousands of tests from Node's own test suite before every release" and headlines **per-module tiers** (🟢 fully / 🟡 partial / 🔴 missing) rather than one number, disclosing granular per-module pass rates where available: `fs` 92%, `zlib` 98%, `dgram`/`dns` >90%, `events`/`os`/`path`/`querystring`/`string_decoder` 100%, `http` ~92%. Principle: "if it works in Node and not in Bun, that's a Bun bug." Source: [bun.com/docs/runtime/nodejs-compat], [socket.dev Bun 1.2].
- **Deno**: the gold-standard *reproducible* model and the one the repo's harness already gestures at. `tests/node_compat/` has `runner/suite/` = a **git submodule** of vendored Node test files (`denoland/node_test`), and **`config.jsonc`** lists exactly which test files are expected to pass, with per-test flags (`windows`/`darwin`/`linux` platform gates, `flaky` = retry up to 3x, `reason` for skips, per-test `env`). The score is computed against **Node's own test suite, not a custom benchmark** — Deno 2.8 reports **76.4%** of Node's suite passing, with a daily viewer at node-test-viewer.deno.dev. Run a single case: `deno test -A node/_tools/test.ts -- test-event-emitter-check-listener-leaks.js`. Sources: [deno node_compat tree], [byteiota Deno 2.8], [denoland/deno_std#2807].

**Takeaway**: a credible score = (executed-pass) / (executed) over a *vendored slice of real upstream Node tests*, gated by a config/manifest, reported per module. The repo harness's denominator design (skip excluded from denominator, per-module table) is already correct; only the *corpus source* is wrong (self-authored, not upstream).

## 5. The single biggest blocker to running REAL Node tests (load-bearing)

The runtime's `eval` path wraps the script in an **indirect eval**: `wrap_source` (libs/runtime/src/lib.rs:536) emits `var __treaty_result = (0, eval)({source_literal});`. Two consequences, both documented in `harness_shim.rs` and proven by the corpus design:
1. **No prelude-injection seam** — the runner hands raw file bytes to `eval`; there's no hook to splice in a shared `common`-like module, so the harness shim is embedded *byte-for-byte in every corpus file* (and a crate test enforces non-drift).
2. **Bare globals are unreachable** — Node's lazy self-replacing global accessors (`process`, `Buffer`, `setTimeout`, `TextEncoder`, `URL`, `console`, `queueMicrotask`) live on the realm global but the indirect-eval scope never triggers those accessors and they're not visible via `globalThis` *from inside that eval*; a test can only reach builtins through `require(...)`. Real upstream Node tests use bare `Buffer`/`setTimeout`/`process` constantly AND `require('../common')` — so **today almost no unmodified upstream Node test can run**. (Note: `lib.rs` tests at 832-1048 show globals DO work via `globalThis` in a *direct* `eval`, so the limitation is specifically the `wrap_source` indirect-eval used by `eval_with_input`/the harness path — fixable.)

## 6. The path to a measurable Node-compat score + closing it

**Phase 0 — make real Node tests runnable (unblock):** Add an `eval_module`/`eval_file`-style entry on `JsRuntime` (or fix the harness path) that runs source in the **realm's own global scope** (so bare `process`/`Buffer`/`setTimeout` resolve via the lazy accessors) AND provides a **`common` shim**: intercept `require('../common')`/`require('../common/*')` to return a Rust/JS-backed module implementing `mustCall`, `mustNotCall`, `mustSucceed`, `hasCrypto`, `skip`, `platformTimeout`, `expectsError`, tmpdir, etc. Implement `mustCall` end-of-process verification by running it in the event-loop drain. This is the prerequisite for everything below.

**Phase 1 — adopt the Deno vendoring model:** Replace (or extend alongside) the hand-authored corpus with a **vendored slice of real upstream Node `test/parallel`** at a pinned Node tag, plus a **`config.jsonc`-style manifest** (extend the existing `known-unsupported.json` into a richer `expected`/`flaky`/`platform`/`flags`/`reason` schema). Seed only modules with real implementations: start with the ones Bun reports 100% on (`events`, `os`, `path`, `querystring`, `string_decoder`) then `buffer`, `util`, `assert`, `url`, `fs`, `zlib`, `crypto`, `timers`, `stream`. The harness's recursive walk, fresh-runtime isolation, per-module scoreboard, and JSON report already support this — point it at the vendored tree.

**Phase 2 — measure + headline:** Emit the JSON `ConformanceReport` per CI run; headline the **executed-pass-rate per module** plus an overall (Deno-style "X% of attempted upstream Node tests"). Stand up a tracked scoreboard (diff the JSON over commits; the report already round-trips serde). Add a CI gate: fail on any *regression* against a checked-in baseline, not on absolute rate, so the number can climb monotonically.

**Phase 3 — close the gap (highest-value `node:` APIs, prioritized by leverage):**

## Research 5


# Edge-runtime standards + conformance vs. Treaty's runtime

## A. The WinterCG / WinterTC "Minimum Common Web Platform API" baseline (the standard to target)

The relevant standard is the WinterCG (now WinterTC, TC55) "Minimum Common Web Platform API" — a curated subset of browser web APIs every server/edge runtime is expected to expose on `globalThis`. It is the basis of ECMA-429 ("2025 snapshot", 1st edition). It is what "match the standard for edge like bun/cloudflare" concretely means. The full required surface (from the spec text at min-common-api.proposal.wintertc.org):

Interfaces required on globalThis:
- DOM/events: `AbortController`, `AbortSignal`, `Event`, `EventTarget`, `CustomEvent`, `ErrorEvent`, `PromiseRejectionEvent`, `MessageChannel`, `MessageEvent`, `MessagePort`, `DOMException`
- Fetch: `Headers`, `Request`, `Response`, `fetch()`
- Files/forms: `Blob`, `File`, `FormData`
- Compression: `CompressionStream`, `DecompressionStream`
- Streams (the FULL set): `ReadableStream`, `ReadableStreamDefaultReader`, `ReadableStreamDefaultController`, `ReadableStreamBYOBReader`, `ReadableStreamBYOBRequest`, `ReadableByteStreamController`, `WritableStream`, `WritableStreamDefaultWriter`, `WritableStreamDefaultController`, `TransformStream`, `TransformStreamDefaultController`, `ByteLengthQueuingStrategy`, `CountQueuingStrategy`
- Encoding: `TextEncoder`, `TextDecoder`, `TextEncoderStream`, `TextDecoderStream`
- URL: `URL`, `URLSearchParams`, `URLPattern`
- Crypto: `Crypto`, `CryptoKey`, `SubtleCrypto`
- Timing: `Performance`
- `WebAssembly.*` (Module/Instance/Memory/Table/Global/Tag/Exception + compile/instantiate/validate)

Global functions: `atob`, `btoa`, `setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`, `queueMicrotask`, `structuredClone`, `reportError`, `fetch`.
Global namespaces/props: `globalThis`, `console`, `crypto`, `performance`, `navigator` (with `.userAgent`), `WebAssembly`. Event handlers: `onerror`, `onunhandledrejection`, `onrejectionhandled`. (Worker scopes additionally expose `self`.)

## B. How each edge runtime defines + proves conformance (the test suites)

- Cloudflare workerd: built-in APIs are web-standard (`fetch`, Streams, Web Crypto). Conformance is proven by running the actual web-platform-tests (WPT) repo inside workerd. The harness lives in `src/wpt/` (a vendored WPT subset + `src/wpt/harness/harness.ts`). Each spec area is a `*-test.ts` driver: `url-test.ts`, `urlpattern-test.ts`, `encoding-test.ts`, `compression-test.ts`, `streams-test.ts`, `WebCryptoAPI-test.ts`, `dom/`, `webidl-test.ts`, `fetch`, `performance-timeline-test.ts`. The harness loads each WPT JS, interpolates `{{host}}`/`{{ports}}`, runs it via `env.unsafe.eval`, implements WPT's `test()`/`async_test()`/`promise_test()` + `assert_*`, and validates results against an `expectedFailures`/`disabledTests`/`omittedTests` allow-list. It is wired as Bazel `.wd-test` targets. Crucially: workerd does NOT pass 100% of WPT — it ships an explicit expected-failures list and gates strictness behind compatibility flags (`pedantic_wpt` for Event/EventTarget strict WPT mode; `internal_stream_byob_return_view`, BYOB ArrayBuffer-detach flags for Streams spec conformance; `nodejs_compat`/`nodejs_compat_v2` for node: builtins). "Passing its test cases" = passing the curated WPT subset minus a maintained skip list, not the entire WPT.
- Bun: ships a Jest-compatible test runner (its own product tests), and additionally vendors web-platform-tests under `test/js/web/` plus runtime API tests; it measures itself against WPT for URL/encoding/streams/fetch/WebCrypto. Same model: vendored WPT + skip list.
- Deno / Deno Deploy: runs the upstream WPT repo via its `./tools/wpt.ts` runner against an `expectation.json` of known-pass tests; this is the most rigorous of the three (Deno was an early WinterCG co-founder).
- Vercel Edge: `vercel/edge-runtime` (open source) is a Node-based polyfill layer providing the WinterCG subset; it advertises a `globalThis.EdgeRuntime` marker and tracks the WinterCG Common Minimum API. Less of a from-scratch engine, more a curated polyfill set.

Common denominator: the bar is the WPT subset for {url, urlpattern, encoding, compression, streams, FileAPI, FormData, WebCryptoAPI, fetch, dom (events), html (structured clone, MessageChannel), performance-timeline, webidl} run under each runtime's own harness, scored against a maintained expected-failures allow-list.

## C. Treaty's runtime reality (libs/runtime — verified by reading the code)

Engine: Nova (pure-Rust JS engine, pinned git rev `bece61ac`), wrapped by `JsRuntime` in `libs/runtime/src/lib.rs`. Two constructors: `JsRuntime::new()` (plain) and `JsRuntime::with_node_compat()` (the WinterCG/Node layer). The Node-compat layer is a module-granular, lazy, low-memory design documented in `libs/runtime/src/node/ARCHITECTURE.md`, with one localized `unsafe` (the Nova HostHooks lifetime extension in `core.rs`) and a real microtask+timer event loop (`event_loop.rs::run_until_idle`, drained after every `eval`).

What is ALREADY wired as globals (from `libs/runtime/src/node/globals.rs::install_module_globals`, lines 262-321):
- Eager: `process`, `console`(per ARCHITECTURE), `Buffer`, timers (`setTimeout/clearTimeout/setInterval/clearInterval/setImmediate/clearImmediate`), `queueMicrotask`, `structuredClone`, `globalThis`/`global`/`self`.
- Lazy self-replacing accessors: `URL`, `URLSearchParams`, `TextEncoder`, `TextDecoder`, `Headers`, `Request`, `Response`, `fetch`, `crypto` (Web Crypto), `Blob`, `File`, `FormData`, `AbortController`, `AbortSignal`, `Event`, `EventTarget`, `performance`, `btoa`, `atob`, `ReadableStream`, `WritableStream`, `TransformStream`.

Backing implementations are genuinely substantial, not stubs:
- `web_globals.rs`: real pure-Rust SHA-1/256/384/512, CSPRNG (`getrandom`), RFC4122 v4 UUID, RFC4648 base64 for btoa/atob, monotonic `performance.now`; `crypto.getRandomValues`, `crypto.randomUUID`, `crypto.subtle.digest` (returns real `Promise<ArrayBuffer>` via the event loop), and JS-level `Blob`/`File`/`FormData`/`Event`/`EventTarget`/`AbortController`/`AbortSignal`. Unit + JS-integration tested (e.g. SHA-256("abc") vector, AbortController dispatch, Blob.text round-trip).
- `web_streams.rs`: a full from-scratch WHATWG Streams implementation (default ReadableStream + controller + reader with pending-read parking, WritableStream + writer with serialized writes/backpressure, TransformStream with flush, async iteration `Symbol.asyncIterator`/`for await`). Promise-driven, drained by the event loop. Well tested.
- `fetch.rs`: full pure-Rust WHATWG header list (case-insensitive, combine, Set-Cookie/getSetCookie, sort-and-combine), method normalization, status classification, `data:` URL processor — AND, contradicting its own older module doc, a REAL HTTP/HTTPS transport: `httpStart`/`httpsStart`/`httpPoll` driving a background reactor in `node:net` with `rustls` TLS (`tls.rs`, deps in Cargo.toml). So `fetch()` against `http(s)://` actually performs network requests, not just `data:`.
- `crypto.rs` (node:crypto): real digests, HMAC, AES-128/256-CBC (`createCipheriv`/`createDecipheriv`), PBKDF2, randomBytes/randomUUID.
- Plus node: builtins: `fs`, `path`, `os`, `url`, `util`, `events`, `stream`, `http`, `https`, `tls`, `net`, `child_process`, `zlib`, `buffer`, `assert`, `querystring`, `string_decoder`, `structuredClone`, etc.

## D. The gap between Treaty's runtime and the WinterCG/edge baseline (honest)

Despite the impressive surface, the gap to "match the standard / pass all the edge test cases" is LARGE. Specifics:

1. MISSING required globals (not wired at all in globals.rs): `CompressionStream`/`DecompressionStream` (the zlib core exists in `zlib.rs` but isn't exposed as the streaming web classes), `URLPattern`, `TextEncoderStream`/`TextDecoderStream`, `navigator` (+`.userAgent`), `reportError`, `DOMException` (referenced defensively as `globalThis.DOMException || Error` in globals.rs:955 — i.e. assumed possibly-absent), `CustomEvent`/`ErrorEvent`/`PromiseRejectionEvent`, `MessageChannel`/`MessageEvent`/`MessagePort`, `CryptoKey`/`SubtleCrypto` as named constructors, `ByteLengthQueuingStrategy`/`CountQueuingStrategy`, the BYOB stream classes, and `WebAssembly` (Nova has no Wasm engine — a hard gap).

2. SubtleCrypto is digest-only. Web Crypto WPT (`WebCryptoAPI-test.ts`) exercises `importKey`/`exportKey`/`generateKey`/`encrypt`/`decrypt`/`sign`/`verify`/`deriveBits`/`deriveKey`/`wrapKey` across AES-GCM/CBC/CTR, RSA-OAEP/PSS/PKCS1, ECDSA/ECDH (P-256/384/521), HMAC, HKDF, PBKDF2, Ed25519/X25519. Treaty implements only `subtle.digest`. This is the single biggest crypto gap; the underlying RustCrypto pieces exist for some (AES-CBC, PBKDF2, HMAC) but none are exposed through `subtle`, and there's no `CryptoKey` object model.

3. Streams: solid default streams, but no byte streams / BYOB readers, no queuing-strategy classes, no `ReadableStream.from`/`tee`/`pipeThrough`/`pipeTo` confirmed, no `Response.body`/`Request.body` integration as real `ReadableStream`. WPT streams + the BYOB ArrayBuffer-detach semantics (which even workerd needed flags for) are not met.

4. No edge "handler" contract. An edge runtime isn't just globals — it's an invocation model: Cloudflare/Vercel/Deno Deploy dispatch a `Request` to either `export default { fetch(request, env, ctx) }` (modules) or `addEventListener('fetch', e => e.respondWith(...))` (service-worker), plus `scheduled`/`queue`/Durable Objects. Treaty's `JsRuntime` is an eval/macro/server-fn evaluator (`run_macro`, `run_server_fn`); there is no Request-in/Response-out request loop, no `FetchEvent`/`ExecutionContext`/`env` binding, no `EdgeRuntime` marker. `libs/treaty-ssr` (new, uncommitted) is the closest thing to a server handler but is a Rust SSR layer, not a JS edge-worker host. So even with perfect globals, Treaty cannot today run a Cloudflare/Vercel/Deno worker entrypoint.

5. No conformance harness at all. There is no WPT vendoring, no WPT harness (`test()`/`async_test()`/`promise_test()`/`assert_*`), no `expectation.json`/expected-failures list, and no CI gate scoring Treaty against any spec suite. Conformance today is asserted only by ~40 hand-written `#[cfg(test)]` unit/integration tests inside each module — good engineering tests, but NOT spec conformance evidence. To credibly claim "passes the edge test cases" you must vendor WPT (url, encoding, streams, FileAPI, FormData, WebCryptoAPI, dom/events, html/structured-clone, urlpattern, compression) and run it under Nova with a tracked allow-list, exactly as workerd/Bun/Deno do.

6. WebIDL conformance details. WPT also checks brand-checks, illegal-constructor behavior, property enumerability/configurability, `[Symbol.toStringTag]`, getter-on-prototype placement, argument coercion/TypeError shapes, and exact error types (`DOMException` with the right `.name`). Treaty's classes are JS-bootstrapped shells over native primitives (necessary because the pinned Nova rev exposes no embedder internal-slot API — documented in fetch.rs:46-51 and text_encoding); these will fail many WebIDL-pedantic WPT subtests (wrong prototype shape, missing brand checks, `Error` instead of `DOMException`).

7. Engine-level limits. The pinned Nova rev lacks an embedder `Uint8Array`-from-bytes constructor (bytes cross the boundary as plain integer Arrays everywhere — see web_globals.rs, fetch.rs, text_encoding), lacks native internal slots for stateful web classes, and has no WebAssembly. These are not Treaty bugs but they cap achievable conformance until Nova advances or those seams land.

## E. How libs/runtime WOULD target edge (the path)

To "target edge / pass edge test cases like bun/cloudflare", the concrete work, in dependency order:
1. Complete the WinterCG global surface in `globals.rs`: add `DOMException` (as a real class, used by every spec for errors), `navigator.userAgent`, `reportError`, `CustomEvent`/`MessageChannel`/`MessageEvent`/`MessagePort`, `URLPattern`, `TextEncoderStream`/`TextDecoderStream`, `CompressionStream`/`DecompressionStream` (wrap the existing `zlib.rs` flate2/brotli core as TransformStreams), and the queuing-strategy + byte-stream classes.
2. Build out `SubtleCrypto` + `CryptoKey` over the RustCrypto crates already in Cargo.toml (extend with `aes-gcm`, `rsa`, `ecdsa`/`p256`/`p384`, `hkdf`, `ed25519-dalek`) — this is the largest single chunk and is the spine of edge auth/JWT workloads.
3. Define the edge handler contract: a Request→Response request loop on `JsRuntime` that loads a module entry, reads `export default { fetch }` (and the service-worker `addEventListener('fetch')` form), constructs the `Request` from the host, binds `env`/`ctx`, and serializes the returned `Response`. This is what makes it an edge HOST, not just a global bag. `libs/treaty-ssr`'s handler is the natural integration point.
4. Stand up a re-runnable WPT conformance harness (mirrors the repo's existing harness-driven culture — see MEMORY's oxc-migration / render3-sync / backend-parity harnesses): vendor the WPT subdirs, implement the WPT JS harness in a Treaty test crate, run each under `JsRuntime::with_node_compat()`, and score against a committed `expected-failures` allow-list so the pass rate is a tracked, ratcheting CI gate.
5. Where Nova blocks conformance (Uint8Array embedder ctor, internal slots, Wasm), file/track upstream Nova seams or pin a newer rev; document each as a known capped subtest set.


**Recommendation:** Treat "edge conformance" as a harness-driven, ratcheting goal, not a one-shot. Concretely: (1) FIRST stand up a re-runnable WPT conformance gate (vendor the WPT subset for url/urlpattern/encoding/compression/streams/FileAPI/FormData/WebCryptoAPI/dom-events/html-structuredClone/performance, implement the WPT harness in a Treaty test crate, run each test under JsRuntime::with_node_compat(), score against a committed expected-failures allow-list) so the pass rate becomes a measurable, tracked number BEFORE claiming any parity — this mirrors workerd/Bun/Deno, which all score against WPT-minus-skiplist, and matches the repo's existing harness culture. (2) Close the highest-leverage surface gaps in priority order: DOMException + navigator + reportError + the event family (cheap, unblocks correct error shapes everywhere) -> CompressionStream/DecompressionStream by wrapping the existing zlib.rs core -> a real SubtleCrypto+CryptoKey over RustCrypto (the biggest and most valuable chunk for edge auth/JWT) -> URLPattern + Encoding streams + byte/BYOB streams + queuing strategies. (3) Add the edge HANDLER contract (Request->export default{fetch}/addEventListener('fetch')->Response loop with env/ctx) so libs/runtime is an edge host, not just a global bag; wire it through libs/treaty-ssr. Do NOT market "passes all the edge test cases like Bun/Cloudflare" until the WPT gate exists and reports a real, high pass rate — today there is zero spec-conformance evidence, only ~40 hand-written module tests. Also note Nova engine caps (no WebAssembly, no embedder Uint8Array ctor, no native internal slots) will hard-limit WebIDL-pedantic subtests; track those as known-capped rather than chase them.

**Risks:** Scope honesty: the surface looks ~70% present by name (most WinterCG globals are wired in globals.rs), but conformance depth is far lower — SubtleCrypto is digest-only (no import/generate/encrypt/sign/verify/derive, no CryptoKey), streams lack BYOB/byte-streams/queuing-strategies, and several required globals (CompressionStream/DecompressionStream, URLPattern, navigator, reportError, DOMException, MessageChannel, Encoding streams, WebAssembly) are missing entirely. WebIDL-pedantic WPT (brand checks, prototype shape, DOMException error types, ArrayBuffer detach) will fail broadly because the web classes are JS shells over native primitives (forced by the pinned Nova rev's lack of internal-slot + Uint8Array embedder APIs). There is NO conformance harness and no CI gate, so any current 'edge-ready' claim is unsubstantiated and a credibility risk. WebAssembly is unimplementable on Nova today (no Wasm engine) — a permanent gap vs. the WinterCG list until the engine changes. There is no edge invocation model (no Request->Response handler, no export default{fetch}/FetchEvent, no env/ctx), so even perfect globals would not let a real Cloudflare/Vercel/Deno worker run. Documentation drift risk: fetch.rs's module-doc still says 'no network/transport' while the code now has a real rustls HTTP/HTTPS reactor (httpStart/httpsStart/httpPoll) — stale comments could mislead a reader about capabilities in either direction. ## What "a package-manager installer for the Treaty runtime" actually means

There are TWO distinct, separable products here. Conflating them is the #1 scope trap. They ship on different timelines.

(A) THE RUNTIME INSTALLER ("how you get `treaty` onto a machine"). This is how Bun/Deno/Node ship the binary: detect platform/arch, download the right prebuilt binary from GitHub Releases (or a CDN), unpack to a per-user dir, put it on PATH. Self-contained, no dependency resolution. This is the SMALL, high-leverage piece and should ship first.

(B) THE PACKAGE MANAGER ("`treaty install <pkg>` resolving node_modules from the npm registry"). This is `bun install`/`pnpm`/`deno add`: fetch packument metadata, solve the version/dependency graph, download+verify tarballs, lay out node_modules. This is the LARGE, multi-quarter piece. Treaty already builds on oxc_resolver (apps/treaty-cli/src/resolve.rs:19, libs/runtime/src/node/module_resolver.rs), which solves only the READ side (specifier -> file). It does NOT solve the WRITE side (registry fetch, SAT-style version solving, tarball extraction, lockfile). That is the bulk of the work.

- One POSIX script at https://bun.sh/install (verified by fetching it) + a PowerShell `irm bun.sh/install.ps1|iex` for Windows.
- Platform detection via `uname -ms`; maps to targets `darwin-x64`, `darwin-aarch64`, `linux-x64`, `linux-aarch64`, `windows-x64`, `windows-aarch64`. Appends `-musl` on Alpine, redirects Rosetta x64 Macs to aarch64.
- CPU feature gate: checks `/proc/cpuinfo`/`sysctl` for AVX2, falls back to a `-baseline` build for older CPUs. (Treaty's Rust binary can avoid this if it doesn't require AVX2 at compile time — one fewer artifact axis.)
- Downloads `https://github.com/oven-sh/bun/releases/{latest|$TAG}/download/bun-$target.zip`, unzips, chmod +x, installs to `$BUN_INSTALL` (default `~/.bun/bin`), appends PATH exports to `.zshrc`/`.bash_profile`/`config.fish`, installs shell completions. Version-pinning is the first positional arg (the release tag). It is a SINGLE-version downloader, NOT a version manager (no list/switch/rollback).
- Bun is ALSO distributed via npm (`bun` wrapper package), Homebrew, Docker, Scoop, and proxies `bun upgrade` for self-update.

BUN — package manager (`bun install`)
- Flat node_modules (npm-compatible layout) with dedupe; npm-registry-compatible (works against npmjs.org and any compatible registry); global cache at `~/.bun/install/cache/${hash}.npm`; once cached, install is just a filesystem link/clonefile, not a copy. Binary lockfile (`bun.lockb`, now also a text `bun.lock`). Written in Zig for syscall-level speed.

DENO
- Runtime installer: `curl -fsSL https://deno.land/install.sh | sh` / `irm https://deno.land/install.ps1 | iex`; same GitHub-releases-per-target pattern. Also Homebrew/Scoop/Cargo.
- Package management (Deno 2+): npm specifiers (`npm:express`), unprefixed names default to npm (`deno add express` == `deno add npm:express`); JSR is the native registry (`jsr:` prefix). Default model is a GLOBAL cache (hard links on Linux, clonefile on macOS — pnpm-style), and it only materializes a real node_modules when a package.json is present or `--node-modules-dir` is set. Version managers exist (dvm) but Deno is mostly single-binary + `deno upgrade`.

NODE
- Official installers: per-platform .pkg/.msi/.tar.gz from nodejs.org/dist; no curl|sh by default.
- Real-world version management is third-party: nvm (POSIX shell, slow — seconds per switch) and fnm (Rust, sub-ms switch). fnm is the closest analog to what Treaty should build: a Rust binary that downloads Node tarballs from the dist server, extracts them, manages multiple versions under `$XDG_DATA_HOME/fnm`, switches via PATH/symlink shims, auto-switches on `cd` reading `.node-version`/`.nvmrc`, and integrates via `eval "$(fnm env)"` in the shell rc.
- Corepack ships INSIDE Node and is the package-manager-version-manager: it pins/shims pnpm/yarn/npm per-project via the `packageManager` field. This is a useful pattern Treaty could mirror to pin a Treaty toolchain version per repo.

PNPM
- Two artifacts: `pnpm` (needs Node, pure ESM since v11) and `@pnpm/exe` (Node bundled into a standalone executable for Node-less systems). Standalone install scripts pick glibc vs musl; notably the standalone script does NOT support Intel Macs (a reminder that the artifact matrix has sharp edges).
- Distributed via npm, Corepack, Homebrew, and standalone scripts.
- The defining feature: a content-addressable global store with hard links + a symlinked nested node_modules (strict, non-flat). This is the most disk-efficient model but the most complex to implement correctly.

================================================================
THE INSTALL UX MATRIX (what users expect)
================================================================
- curl|sh + PowerShell irm|iex: the table-stakes one-liner. Cheap; mostly a shell script + a release pipeline.
- npm -g / a wrapper npm package: free reach into the Node ecosystem; lets `npx treaty` work. Low effort (a postinstall that downloads the right binary, like esbuild/swc do).
- winget (Windows) + Homebrew (mac/Linux) + Scoop/Chocolatey: package-manager-native installs; each needs a manifest PR per release (automatable in CI). Homebrew/winget are the highest-trust channels for non-curl-pipe users.
- A version manager (fnm-style): only worth building once there are multiple Treaty releases people need to pin/switch between. Premature early.
- Self-update (`treaty upgrade`): trivial once the release/download path exists; Bun/Deno both ship it.

================================================================
THE PACKAGE-MANAGER PIPELINE (what `treaty install` must implement)
================================================================
From the npm registry docs (verified): a client must
1. Fetch the ABBREVIATED packument: GET `https://registry.npmjs.org/<pkg>` with `Accept: application/vnd.npm.install-v1+json` (the "corgi" doc — ~10x smaller; contains `dist-tags`, `versions{name->{dependencies, optionalDependencies, peerDependencies, bin, engines, dist:{tarball,integrity}}}`). Use ETag caching.
2. Resolve semver ranges against `versions`/`dist-tags`, recursively, into a full dependency graph (this is the hard part — backtracking/peer-dep satisfaction; npm uses an arborist, this is genuinely complex).
3. Download each `dist.tarball`, verify `dist.integrity` (SRI `sha512-<base64>`), extract to a content-addressable cache.
4. Lay out node_modules (flat hoisted like npm/bun, or symlinked-strict like pnpm) and write a lockfile.

CODEBASE REALITY (what Treaty already has vs. needs)
- Already has: a native Rust CLI (apps/treaty-cli, clap-based, plugin registry) with build/serve/generate/compile; oxc_resolver 11.20.0 wired in two places for READ-side resolution (apps/treaty-cli/src/resolve.rs, libs/runtime/src/node/module_resolver.rs); a pure-Rust Node-compat runtime (libs/runtime) with node:crypto (sha2/hmac — reusable for integrity), node:zlib (flate2/brotli — reusable for tarball decompression), node:tls/https (rustls — reusable for the registry HTTP client). The runtime ARCHITECTURE.md notes fetch is currently a transport-free stub ("a real transport behind the event loop is a tracked follow-up").
- Does NOT have: any installer script, any release/binary-distribution pipeline, any `treaty install`/`add` command, any registry client, any version solver, any lockfile, any tarball extractor wired into a store. There is a `verdaccio` devDependency (a local npm registry) — useful as a test fixture for a future PM, but nothing consumes it yet.
- Strong reuse opportunities: oxc_resolver for node_modules layout validation/read; the runtime's rustls/sha2/flate2/brotli/tar-capable crates for the fetch+verify+extract path; clap plugin registry for the new subcommands. A tar crate (e.g. `tar`) is NOT yet a dependency and would be needed.
- Distribution friction: the release binary uses `lto = true` (Cargo.toml) and `nova_vm` pinned to a git rev (libs/runtime/Cargo.toml) — fine for a binary, but the git-pinned engine means reproducible release builds need that rev vendored/locked. The CLI binary is named `treaty` (apps/treaty-cli/Cargo.toml [[bin]]).

================================================================
KEY DESIGN DECISION: npm-registry-compatible vs bun-like
================================================================
Recommend NPM-REGISTRY-COMPATIBLE, BUN-LIKE LAYOUT. Treaty's whole value prop (per repo memory + README) is "ingest ANY Angular app and just work." Angular apps live on the npm registry (@angular/*). A bespoke registry would be ecosystem suicide. So:
- Registry protocol: speak the npm registry HTTP API (abbreviated packument + tarball + SRI integrity), honor `.npmrc` (registry URL, scopes, auth tokens, proxies) so corporate registries (Verdaccio/Artifactory/GitHub Packages) work.
- Lockfile: read EXISTING npm/pnpm/bun/yarn lockfiles where possible (so adoption is non-destructive), and write your own only as an optimization. Do NOT invent an incompatible-by-default lockfile.
- node_modules layout: flat-hoisted (npm/bun compatible) is the safe default — Angular's tooling and many transitive deps assume hoisting. pnpm-style strict symlinks are a later opt-in, not the default, because Angular's ecosystem has known hoisting assumptions.
- Cache: content-addressable global store + hard-link/reflink into node_modules (the bun/pnpm/deno consensus) for speed and disk.

**Recommendation:** Build the INSTALLER first and the PACKAGE MANAGER second — they are separate products and should not block each other.

1. Installer (ship in weeks): a cross-compile + GitHub Releases pipeline producing `treaty-{os}-{arch}` artifacts with SHA256SUMS; a Bun-cloned `install.sh` + `install.ps1` one-liner (platform detect -> download -> verify -> ~/.treaty/bin -> PATH); an npm wrapper package with per-platform optional binaries (esbuild/swc pattern) so the Angular/npm audience gets `npm i -g treaty` and `npx treaty` for free; Homebrew/winget/Scoop manifests automated on tag; and a `treaty upgrade` self-update. DEFER the fnm-style multi-version manager — and when needed, prefer a Corepack-style PER-PROJECT toolchain pin over a global switcher (cheaper, better fit for a compiler).

2. Package manager (multi-quarter; phase it): an npm-registry-COMPATIBLE, bun-like client in a new libs/treaty-pm crate plugged into the existing clap registry. Be honest that this is the large piece: the version/dependency SOLVER is the genuinely hard, multi-thousand-line core; the registry protocol, semver, and lockfiles must be CONSUMED (npm-compatible), never reinvented. Maximize reuse: oxc_resolver (already wired) for node_modules read/validation; the runtime's sha2 (integrity), flate2/brotli (decompress), and rustls (HTTPS — finishing the runtime's stubbed `fetch` as a side effect). Add only a `tar` crate. Ship in phases: P0 frozen-lockfile materialization (no solver, immediate CI value), P1 registry+tarball fetch into a content-addressable store, P2 the full solver+lockfile, P3 pnpm-strict layout/workspaces/add-remove-update.

Default choices: npm-registry-compatible protocol; flat-hoisted node_modules (Angular ecosystem assumes hoisting); content-addressable global store with hard-link/reflink (bun/pnpm/deno consensus); read existing lockfiles (non-destructive adoption). This keeps Treaty's "ingest any Angular app" promise intact while delivering the install UX users expect.

**Risks:** SCOPE / EFFORT (be honest)
- The package manager is genuinely a multi-quarter effort dominated by the dependency SOLVER (peer deps, backtracking, conflict resolution). npm's arborist and bun/pnpm's solvers are large, battle-hardened, and full of ecosystem-specific edge cases. Underestimating this is the central risk. The installer, by contrast, is weeks.
- A correctness bug in node_modules layout or version solving silently breaks user builds — the bar is "matches npm/bun exactly," and proving that requires a broad conformance corpus (the existing `verdaccio` devDependency can seed a local-registry test harness).

DISTRIBUTION / BUILD
- Reproducible release builds are at risk because nova_vm is pinned to a git rev (libs/runtime/Cargo.toml), not a crates.io version, and `lto = true` is on. Lock the rev in Cargo.lock and pin the toolchain (rust-toolchain.toml exists) before cutting releases.
- The artifact matrix has sharp edges: glibc vs musl, Apple Silicon vs Intel, Windows ARM, signing/notarization (macOS Gatekeeper, Windows SmartScreen). pnpm's standalone script dropping Intel Macs is the cautionary tale. Notarization/code-signing is an operational cost, not a coding one, and is easy to forget.
- curl|sh and irm|iex are trust-sensitive; ship checksums + (ideally) signatures, and a Homebrew/winget path for users who refuse pipe-to-shell.

RUNTIME COUPLING
- The runtime's `fetch` is currently a transport-free STUB (libs/runtime ARCHITECTURE.md). If the PM reuses the runtime's HTTP path, you must finish that transport first; the lower-risk path is to give the PM its own rustls-backed HTTP client and backport it to the runtime later.
- A `tar` crate is not yet a dependency; adding tarball extraction is new surface (path-traversal/zip-slip safety must be handled).

ECOSYSTEM
- pnpm-style strict symlinked node_modules breaks some Angular/transitive packages that assume hoisting; defaulting to it would violate the "ingest any Angular app" promise. Keep flat-hoisted as default.
- A bespoke/incompatible lockfile or registry would fragment Treaty from the npm ecosystem it depends on (@angular/*). Compatibility is non-negotiable.

SEQUENCING
- Don't build the fnm-style multi-version manager prematurely (no multi-release demand yet) — it's effort spent before the need exists. Corepack-style per-project pinning is the cheaper, better-fit alternative when the need arrives.

## Unified architecture

UNIFIED ARCHITECTURE — "structs as a flag through the existing seams; shared-memory as a runtime capability that mostly does not yet exist."

The whole feature decomposes into FIVE layers, each landing on an existing Treaty chokepoint rather than a new subsystem. Critically, the data-plane (parse->IR) is fully tractable and additive; the runtime-plane (shared heap + threads) is where the engine simply lacks the capability and 80% of the real work lives.

LAYER 1 — OXC PARSE (front of the existing ParseBackend seam).
oxc 0.133 has NO StructDeclaration/SharedStruct AST node (verified: C:\...\oxc_ast-0.133.0\src\ast\js.rs). `struct`/`shared` are CONTEXTUAL keywords (not reserved), so source containing them today either ASI-errors or mis-parses as an expression. Two acquisition paths, gated behind the SAME ParseBackend trait that already isolates oxc from the facade (d:\dev\treaty\libs\treaty-ivy\facade\src\parse\mod.rs — the single CHOKEPOINT, only file allowed to `use oxc_`):
  (a) Preferred: land StructDeclaration in oxc upstream (parser branches on `struct`/`shared struct` in statement position per the Stage-2 grammar, reusing ClassHeritage/ClassElementList; enforce the `[no LineTerminator here]` ASI constraints and the shared-struct early errors — null proto implicit, NO instance methods/getters/setters, fields+static+ctor only). Until merged, vendor a thin oxc fork or a pre-scan.
  (b) Bridge: a pre-parse recognizer in OxcParseBackend that detects struct/shared-struct declarations, records their span+shape, and rewrites them to a sentinel `class` (carrying a struct marker) before handing to oxc — so the rest of the pipeline is unblocked while (a) lands. Both paths produce the SAME neutral output, so they are interchangeable behind the seam.

LAYER 2 — NEUTRAL IR (treaty_ivy_core::neutral, d:\dev\treaty\libs\treaty-ivy\core\src\neutral.rs). This is the keystone and it is purely ADDITIVE — no existing field changes, so matchGolden stays byte-identical for non-struct code:
  - Add `MemberKind` is unchanged; struct-ness is a CLASS-level concern. Add to `ClassWithDecorators` (the type the decorator layer reads via treaty_ivy_decorators::registry::ClassMeta): `struct_kind: StructKind` where `enum StructKind { None, Struct, SharedStruct }` (defaulting to `None`), plus `super_struct: Option<...>` reusing the existing heritage representation, and a per-field `fixed_layout` invariant carried implicitly by struct_kind.
  - Add the atomic-field-access surface: `Atomics.load/store/exchange/compareExchange(structVal, "field")` is recognized in the NExpr lowering as a tagged AtomicFieldOp so emit can preserve it 1:1. Default (non-atomic) shared-struct field reads/writes lower unchanged.
  - The neutral IR is the single source of truth both backends (oxc, swc) must fill IDENTICALLY — this is what backend-parity gates. swc gets the same struct_kind flag (swc has no struct node either, so the swc backend uses the same bridge-recognizer strategy).

LAYER 3 — RUNTIME / NOVA (libs/runtime). This is the honest hard wall. Current reality (verified d:\dev\treaty\libs\runtime\src\lib.rs): ONE `GcAgent` per `JsRuntime`, `DefaultHostHooks`, single isolate, no SharedArrayBuffer/Atomics/Worker surface, the one localized `unsafe` lifetime-extension. Nova has NO shared heap. So:
  - Sub-layer 3a (tractable, polyfillable): UNSHARED `struct` lowers to `class` + Object.seal (fixed layout, pre-init fields to undefined, sealed). Semantically close; loses the engine fast-path (acceptable — Nova has no struct fast-path anyway) and cannot perfectly enforce non-genericity. Ships first.
  - Sub-layer 3b (NOT polyfillable — requires real engine work): `shared struct`, `SharedArray`, tear-free unordered field access, `Atomics.load/store/exchange/compareExchange` field overloads, `Atomics.Mutex`/`Atomics.Condition`, and non-copying cross-agent postMessage. None can be shimmed in userland. This needs (i) a Nova shared-heap (analogous to V8 crbug v8:11708 — a heap shared between isolates with shared GC at a safepoint), (ii) multiple Nova agents on real OS threads (Nova's GcAgent is currently single-threaded; the one `unsafe` lifetime model and `DefaultHostHooks` assume one agent), (iii) a thread-safe shared-object allocator + shared string table, and (iv) a worker_threads/MessageChannel surface that postMessages a HANDLE (not a structured clone — note structured_clone.rs deliberately COPIES, the opposite semantics). This is a multi-quarter engine effort, very likely requiring upstream Nova contributions, and is the dominant cost of the whole initiative.
  - Runtime-selection rule (memory: Nova ONLY for the pure-Rust axum path) still holds: JS-runtime backends (Bun/Node/edge) get shared-structs from THEIR engine (V8's SharedStructType API / Bun), so Treaty's job there is lowering syntax->engine-API, not building a heap.

LAYER 4 — CONFORMANCE (the gates; reuse + extend existing harnesses). Three independent scoreboards, each a re-runnable no-AI harness in tools/ (the Treaty workflow style):
  - struct PARSE parity -> tools/backend-parity (oxc vs swc fill struct_kind/atomic ops byte-identically) + the existing parse_parity test + matchGolden-185 must stay green for all non-struct corpus.
  - Node test-suite -> tools/node-conformance ALREADY EXISTS (runs Node test/parallel-style .js through JsRuntime::with_node_compat, PASS/FAIL/SKIP+reason, known-unsupported.json manifest). Extend its corpus with V8/Node `--harmony-struct` struct tests and worker_threads shared-struct tests; today they SKIP as known-gap, becoming the burndown metric.
  - edge/WinterCG/WPT -> a NEW sibling harness `tools/edge-conformance` modeled identically on node-conformance, running WPT structured-clone/Atomics/SharedArrayBuffer subsets + WinterCG minimum-common-API tests, with a per-target (Bun/Cloudflare/Node-edge) skip manifest. crossOriginIsolated / COOP+COEP gating is recorded as an environment precondition.

LAYER 5 — INSTALLER + PACKAGE MANAGER. The runtime binary + a pm that resolves/installs the runtime and packages. Reuses oxc_resolver 11.20.0 (already a dependency, Node-style node_modules/exports/conditions resolution). The installer ships the treaty_runtime binary (version-pinned to the Nova rev + the struct capability level it supports) and a capability manifest declaring whether THIS build has shared-heap/threads, so a package can require a minimum capability level and fail fast rather than racily. This layer is the most independent and can proceed in parallel once Layer 3a exists; it does NOT block on 3b.

  - Neutral-IR extension (one defaulted enum field) — provably byte-identical, matchGolden-185 untouched.
  - struct parse behind ParseBackend — the seam already exists precisely for engine swaps; the bridge-recognizer approach unblocks everything without waiting on upstream oxc.
  - backend-parity for structs — reuses the harness you already gate on.
  - Unshared `struct` -> class+Object.seal lowering — fully polyfillable; Nova runs it today. Semantically close (fixed layout, pre-init fields, sealed); the two honest losses are (a) the engine fast-path that is the proposal's whole point — irrelevant since Nova has no struct fast-path anyway — and (b) perfect non-genericity enforcement, which a transpile cannot guarantee.
  - node-conformance extension + a parallel edge/WPT harness — both are no-AI, deterministic, scoreboard-style, exactly the Treaty pattern; the second is a near-copy of the first.
  - Installer + pm on oxc_resolver — independent, parallelizable, depends only on a runnable runtime.

GENUINELY HARD (quarters, likely upstream Nova contributions, the dominant cost):
  - SHARED-MEMORY THREADING is NOT polyfillable — the findings are explicit and the codebase confirms it. `shared struct`/`SharedArray`/tear-free fields/atomic field ops/`Atomics.Mutex`/`Atomics.Condition`/non-copying postMessage all require a real shared heap and multiple agents on real threads. None can be shimmed in userland.
  - Nova reality (verified, d:\dev\treaty\libs\runtime\src\lib.rs): ONE GcAgent per JsRuntime, DefaultHostHooks, a single isolate, and the one localized `unsafe` lifetime-extension that ASSUMES a single agent. There is NO shared heap, NO SharedArrayBuffer/Atomics surface, NO worker_threads. Building a shared heap with a shared-GC safepoint (the V8 crbug v8:11708 analogue), a shared string table, a thread-safe shared-object allocator, and a handle-transferring postMessage that is the OPPOSITE of the existing structured_clone (which deliberately COPIES) is a from-scratch engine subsystem. Even V8's own mid-2025 ship target is "widely viewed as optimistic" per the findings; a pure-Rust engine reimplementing it is a major, risk-laden, schedule-uncertain effort almost certainly requiring upstream Nova work outside this repo's control.
  - The proposal itself is Stage 2 — the syntax (computed/symbol field names, StructExpression) and semantics can still move, so any oxc grammar work and any IR shape carries churn risk.

MITIGATION baked into the design: the runtime-selection rule already says Nova is ONLY the pure-Rust axum path; JS-runtime backends (Bun/Node/edge) get shared-structs from THEIR engine, so Treaty's obligation there is syntax->engine-API lowering, NOT building a heap. That means full USER VALUE (shared structs on Bun/Node/edge targets) is reachable via M2-M4 + lowering + M8 WITHOUT the M6/M7 Nova heap — the Nova shared heap is required only for shared-memory on the pure-Rust axum path specifically. Recommend explicitly DEFERRING M6/M7 as a separately-budgeted track and shipping the tractable 80% (parse + unshared structs + lowering-to-engine + conformance + installer) first.

## Completeness critique

### Gaps
VERIFIED-AGAINST-SOURCE: Every concrete codebase claim in the design checks out. No StructDeclaration/SharedStruct in oxc 0.133 ast (grep empty). neutral.rs, the ParseBackend chokepoint, tools/node-conformance, structured_clone.rs, the single `unsafe` extend_lifetime, and the SKIP'd worker_threads case all exist exactly as described. So the critique is about what is MISSING, not what is wrong.

== TIER-1 GAPS (omissions that sink the initiative or the brief's explicit asks) ==

G1. PACKAGE MANAGER / SUPPLY-CHAIN: ENTIRELY ABSENT. The brief explicitly asks for "security of a package manager (supply chain)" and the design says NOTHING about it — no integrity hashes, no lockfile/provenance, no registry, no signing, no install sandbox. Grep for package-manager/lockfile/integrity/sigstore/provenance in *.rs found only incidental hits ("registry" = the decorator registry). This is not under-scoped, it is a 100% missing layer. If a PM is in scope it needs its own design (TUF/sigstore-style signed metadata, SHA-512 subresource integrity in the lockfile, no-install-scripts-by-default or a sandboxed install à la Bun/pnpm, a vetted dependency-confusion / typosquat guard, SBOM emit). If a PM is NOT in scope, the design must say so explicitly — silently dropping a brief item is the worst outcome.

G2. SHARED-STRUCT GC + DATA-RACE SAFETY: HAND-WAVED as "shared GC at a safepoint (analogous to v8:11708)" with zero mechanism. This is the single hardest part of the whole thing and the design spends one parenthetical on it. Missing entirely: (a) how a STOP-THE-WORLD safepoint is reached across N independent Nova `GcAgent`s that today are single-threaded and assume one agent — every agent must rendezvous at a safepoint before the shared heap can be traced, which is a global barrier the current `DefaultHostHooks`/one-agent model has no hook for; (b) what GC algorithm the shared heap uses (Nova is a moving/compacting GC per its design — a MOVING collector on a heap shared across threads requires read/write barriers or handle indirection so a concurrent thread does not dereference a moved object: the design never says whether shared objects are pinned/non-moving or barrier-protected); (c) cross-heap reference direction: per-agent heaps holding refs INTO the shared heap (roots for the shared trace) vs. the illegal reverse (shared object referencing a thread-local object) — the early-error that forbids the latter is unspecified; (d) the shared string table is named but its concurrency model (lock? lock-free interning? per-agent caches?) is absent; (e) "tear-free unordered field access" is asserted as a goal but the memory model (which accesses are SeqCst vs relaxed, how non-atomic field writes avoid tearing on a shared object without a per-field lock) is undefined. This is where the brief's "data-race safety across threads in Rust/Nova" lives and it is the thinnest part of the doc.

G3. OXC UPSTREAM ACCEPTANCE / FORK BURDEN: OVER-OPTIMISTIC and under-analyzed. The design assumes oxc will accept a StructDeclaration for a Stage-2 (NOT Stage-3, NOT shipping) proposal. oxc tracks the TC39 pipeline and TypeScript; it has historically been reluctant to carry non-Stage-3 / non-shipped syntax in the core AST because every AST node is a maintenance + semantic-analysis + codegen + minifier surface forever. Realistic outcome: upstream says "come back at Stage 3 / when TS supports it," and Treaty is left on path (b) the bridge-recognizer OR a permanent vendored fork. The design treats (a) as "preferred" and (b) as a temporary bridge, but the HONEST default is that (b)/fork is the long-term reality, and the design under-scopes the fork-maintenance tax (rebasing a parser patch across oxc's fast release cadence — they shipped 0.29→0.133 in the window this repo already tracks). Also unanalyzed: TypeScript itself has no `struct` syntax, so tsgo/oxlint/the type layer (memory: typecheck with tsgo, lint with oxlint) will ALL reject struct syntax — the design's parse story ignores that the rest of the declared toolchain (tsgo, oxlint, the LSP) also needs struct awareness or the editor/typecheck experience is broken.

G4. "PASS ALL NODE TEST CASES" + "ALL EDGE TEST CASES" IS UNACHIEVABLE AS STATED, and the design half-admits it without quantifying. Node's own test/ suite is tens of thousands of cases bound to V8-specific behavior (error message text, stack format, --harmony flags, ICU/Intl exactness, perf timing, libuv-specific fs/net edge semantics, V8 heap snapshots). Nova will NEVER pass V8-message-text or V8-snapshot tests. The achievable subset is the BEHAVIORAL Node-API conformance (the design's existing corpus shape), NOT "ALL Node test cases." The brief explicitly asks which subsets are achievable — the design does not enumerate them. Honest tiering: ACHIEVABLE = pure-JS-semantics + documented public Node module behavior (fs/path/url/buffer/events/streams/crypto-vectors — already the corpus); NOT ACHIEVABLE = anything asserting V8 internals, exact diagnostic strings, native addons (N-API/node-gyp), worker_threads-with-shared-memory until 3b lands, perf/timing tests, and most of `parallel/` that uses internal/test/common harness assumptions. Same for WPT/edge: structured-clone + Atomics + SAB subsets are gateable; the FULL WPT (DOM, HTML parsing, CSS, full streams) is not, and WinterCG "minimum common API" is a moving target with no frozen version pinned.

== TIER-2 GAPS ==

G5. CONFORMANCE SUITE THE RESEARCH MISSED: test262 (the ECMAScript conformance suite) is the single most important gate for a JS ENGINE adding SYNTAX, and it is not mentioned. The shared-struct proposal ships test262 staging tests under test/staging/explicit-resource-management-adjacent dirs and `--harmony-struct` gated 262 tests; those — not Node's test/ — are the authoritative struct-semantics conformance. The design's three scoreboards (backend-parity, node-conformance, edge-conformance) omit test262 entirely. Also missing: a differential-fuzzing gate (run struct programs on V8 `--harmony-struct` and on Nova, diff results) which is the only credible way to claim semantic parity for a hand-built engine feature.

G6. THE PROPOSAL IS A MOVING TARGET / STALENESS RISK. The design pins behavior to "the Stage-2 grammar" and "V8's SharedStructType API" as if frozen. The TC39 structs+shared-structs proposal has churned (struct/shared struct keyword choices, Atomics.Mutex/Condition naming, whether unshared structs even stay in the proposal). Building a parser + IR + engine semantics against a Stage-2 spec means rework when it advances or splits. No spec-version pin, no "which revision/commit of the proposal" anchor, no plan for proposal churn. Memory note "Today's date is 2026-06-04" — the design should cite the CURRENT proposal stage, not "Stage-2" generically.

G7. CROSS-AGENT postMessage HANDLE is named but the LIFETIME/ROOTING story is missing. Passing a HANDLE (not a clone) across agents means the shared object is now reachable from two heaps; the design does not say how the sending agent's GC knows the object is still live (it must remain rooted by the shared heap, not the sender's local heap), nor how a SharedArrayBuffer-style refcount/ownership works when the last referencing agent dies. This is a use-after-free vector the "data-race safety" brief item demands be addressed.

G8. DEADLOCK / PRIORITY-INVERSION surface from Atomics.Mutex/Atomics.Condition is unmentioned. Adding userland-visible blocking primitives to a runtime whose event loop (verified: node/event_loop run_until_idle, single-threaded microtask pump) assumes non-blocking cooperative execution means a Mutex held on the main agent can deadlock the loop. No design for blocking-on-main detection (V8 disallows Atomics.wait on the main thread for exactly this reason) — the design must replicate that restriction.

G9. SECURITY OF shared memory itself (beyond the PM): SharedArrayBuffer + high-res timers + crossOriginIsolated is a Spectre side-channel surface. The design mentions COOP+COEP gating "recorded as an envi…" (text is truncated mid-word) but the THREAT (timing side-channels, why crossOriginIsolated exists) is not stated, and for the SERVER/pure-Rust axum path there is no browser COOP/COEP — so what gates SharedArrayBuffer there? Undefined.

### Corrections
CORRECTIONS / RE-SCOPING:

C1. Reclassify the runtime-plane honestly. The design's own "80% of the work is in the runtime, and 3b is not polyfillable" is CORRECT and is the best thing in the doc — but then it lists 3b as one bullet of one layer. Promote shared-heap-GC + multi-agent-threading to its OWN top-level program with its own multi-quarter milestone plan, because it is the critical path and everything else (parse, IR, conformance) is comparatively trivial and can ship in weeks. The current 5-layer framing makes a 1-week job (Layer 1-2) look equal in weight to a multi-quarter engine rewrite (Layer 3b). That false symmetry is the document's main framing flaw.

C2. Drop "pass ALL Node test cases / ALL edge test cases" as a goal. Replace with an explicit ACHIEVABLE-SUBSET manifest (see G4 tiering) and make the burndown metric "% of the curated behavioral subset," NOT "% of Node's test/." Otherwise the gate can never go green and the metric is demoralizing/meaningless.

C3. Make path (b) the bridge-recognizer the PLANNED PERMANENT path, with upstream-merge (a) as an OPTIONAL upside, not the "preferred" path the schedule depends on. Budget explicit fork-rebase cost. And add struct-awareness to tsgo + oxlint + the LSP to the scope, or scope the feature to "compile-only, no editor/typecheck support v1" explicitly.

C4. Add test262 (`--harmony-struct` staging) + a V8-differential fuzzer as a FOURTH scoreboard alongside the three. This is the authoritative engine-semantics gate and its omission is the biggest conformance-research miss.

C5. The "Atomics.load/store/... recognized in NExpr lowering as a tagged AtomicFieldOp" — note Atomics on struct fields is a method-call SHAPE, not new syntax, so it needs NO parser change and NO oxc fork; it is a pure emit/runtime concern. The design correctly puts it in the IR but over-couples it to the struct parse work; decouple it (it can land/test independently against SharedArrayBuffer today).

C6. For the pure-Rust axum path: either (a) explicitly DROP shared-structs there for v1 (lower `shared struct` → sealed class, accept reduced semantics, ship), since Nova has no shared heap and building one is the multi-quarter cost — and route all REAL shared-struct workloads to the JS-runtime backends (Bun/V8) per the existing runtime-selection rule; or (b) commit to the Nova shared-heap as a funded upstream contribution with a named owner. The design lists both but does not DECIDE; the roadmap needs the decision because it determines whether this is a 1-month or 12-month initiative.

C7. Add a package-manager security design or explicitly mark it out-of-scope (see G1). Do not leave the brief item silently unanswered.

### Verdict
SOUND ON THE DATA-PLANE, HOLLOW ON THE RUNTIME-PLANE AND THE BRIEF'S TWO HARDEST ASKS (shared-memory safety, package-manager supply-chain). Every codebase claim I checked is accurate (oxc has no struct node; neutral IR / ParseBackend chokepoint / node-conformance / structured_clone all exist as described), so the design is well-grounded and Layers 1-2 are genuinely actionable and additive (matchGolden stays green — credible). But the document's central flaw is FALSE SYMMETRY: it presents a ~1-week parse/IR job and a multi-quarter shared-heap-GC engine rewrite as co-equal layers, and it spends one parenthetical ("safepoint, analogous to v8:11708") on the exact thing the brief demands depth on — cross-thread GC + data-race safety. Two brief items are effectively unanswered: package-manager supply-chain (TIER-1, 100% absent) and the realism of "pass ALL Node/edge tests" (asserted, not subsetted — it is unachievable and must be reframed as a curated behavioral subset). test262 — the authoritative engine-syntax conformance suite — is missed entirely.

FIX FIRST, IN ORDER: (1) DECIDE the axum-path question — drop shared-structs to sealed-class for v1 and route real workloads to the V8/Bun backend, OR fund the Nova shared-heap as a named multi-quarter upstream effort; this one decision determines whether the project is 1 month or 12. (2) Write the actual shared-heap-GC + multi-agent-threading + handle-rooting + Atomics-blocking-on-main design (G2/G7/G8) — it is the critical path and currently a stub. (3) Reframe the Node/edge goal as an explicit achievable-subset manifest and add test262 + a V8-differential fuzzer as a fourth gate (G4/G5). (4) Either design the package-manager supply-chain story or explicitly scope it out (G1). (5) Demote oxc-upstream-merge from "preferred/load-bearing" to "optional upside," budget the permanent fork/bridge, and add struct-awareness for tsgo+oxlint+LSP or scope the editor experience out (G3). Layers 1, 2, and 4 (minus test262) are ready to build now; Layer 3b is not yet a plan, only a wall correctly identified.
